# LLM Wiki 스키마

`docs/`는 이 프로젝트(vision-lab)의 **LLM Wiki**다.
RAG처럼 질문할 때마다 원자료를 다시 찾는 대신, LLM이 원자료를 읽고 위키에 **누적·통합**한다.
사람은 자료 수집·방향 제시·질문을 맡고, 요약·교차참조·정리·장부 관리는 전부 LLM이 맡는다.

## index.md / log.md

- `index.md`: 대분류(`공통`, `Phase 0`~`Phase 4`) → 중분류 → 페이지 목록. "목차 구성 지침"을 따른다.
  각 줄: `- [slug](phase_N/종류/slug.md) — 한 줄 요약`. 모든 ingest마다 갱신.
- `log.md`: 새 기록은 기존 첫 항목 위에 추가한다.
  모든 항목은 다음 형식으로 시작한다.

```
## [YYYY-MM-DD] ingest | 소스 제목
- 생성: [a](phase_0/entities/a.md), [b](phase_0/sources/b.md)
- 갱신: [c](phase_0/analyses/c.md), [overview](overview.md)
```
  작업 종류: `ingest` / `query` / `lint` / `schema`.
  최근 기록 확인: `grep "^## \[" wiki/log.md | head -5`

## 목차 구성 지침

목차(`wiki/index.md`)는 LLM이 페이지를 찾는 입구다. 목차가 커질 때 성능을 떨어뜨리는 원인은 개수 자체보다 **평면 나열, 의미 중복, 서술형 이름**이다. 항목 수는 **200개를 넘지 않게** 유지하되, 아래 규칙을 함께 지킨다.

### 1. 계층 구조 — 평면 나열 금지
- 최상위 대분류는 `공통`과 Phase 5개로 고정한다. 그 아래에 중분류, 그 아래에 페이지를 두는 트리 구조로 만든다.
- 한 분류 아래 페이지가 **20개를 넘으면** 중분류로 나눈다.
- 중분류가 커지면 `index.md`에는 중분류 허브 페이지만 걸고, 개별 페이지 목록은 허브 페이지로 옮긴다. LLM은 `index.md` → 허브 → 페이지 순서로 필요한 부분만 읽는다.

### 2. 의미 중복 금지
- 새 페이지를 만들기 전에 이름이나 주제가 겹치는 기존 페이지가 있는지 확인한다. 겹치면 **새로 만들지 않고 기존 페이지를 갱신하거나 병합**한다.
- 비슷한 이름의 페이지가 둘 이상 필요하면, 목차 설명에 서로의 **차이와 범위**를 명시한다. 예: "탐지 대상(라벨 기준)" vs "시스템 요구사항(동작·성능)".
- 같은 단어로 시작하는 페이지가 여럿 생기면 하나의 중분류로 묶는다.

### 3. 키워드 중심 이름 — 서술형 금지
- 페이지 이름과 목차 항목은 **고유 명사·핵심 키워드로 시작**한다. 데이터셋 번호, 모델명, 도구명, 시스템 구성 요소를 쓴다. 예: `aihub-101-bbox`, `libreyolo-training`, `dataset-yaml`.
- 문장형·시점 의존 이름은 쓰지 않는다. 예: "지난번 논의에서 정한 라벨 규칙" 대신 `detection-target-spec`.
- 목차의 한 줄 설명도 **키워드를 앞에** 두고 짧게 쓴다. 예: `— YOLO 변환, 카메라 단위 분할, 데이터 YAML`.

### 4. 필요한 부분만 읽기
- LLM은 질의할 때 `index.md` 전체를 매번 통째로 쓰지 않는다. 대분류와 중분류로 범위를 좁힌 뒤 관련 페이지만 읽는다.
- 이 방식이 가능하도록 분류 이름과 설명을 질문에서 찾기 쉬운 키워드로 유지한다.

### 점검
- 페이지를 추가하거나 lint할 때 다음을 확인한다: 총 항목 수(≤ 200), 대분류 수(공통 + Phase 5개), 분류별 항목 수(≤ 20), 이름·주제 중복, 서술형 이름.

## 층 구성

| 층 | 경로 | 소유 | 규칙 |
|---|---|---|---|
| Raw sources | `raw/` | 사람 | **불변.** LLM은 읽기만 하고 절대 수정·이동·삭제하지 않는다. 진실의 원천. 이미지는 `raw/assets/` |
| Wiki | `wiki/` | LLM | LLM이 전부 작성·유지. 사람은 읽기만 한다 |
| ADR | `adr/` | 공동 | 결정 기록. 위키 밖에 둔다. "결정 기록 (ADR)" 절을 따른다 |
| Schema | `AGENTS.md` (이 파일) | 공동 | 규칙이 바뀌면 사람과 합의 후 갱신 |

## Wiki 구조

최상위 폴더는 **Phase**다. Phase 폴더 안의 하위 폴더는 페이지의 **종류**다.
Phase 정의는 [overview](wiki/overview.md)의 진행 단계를 따른다.

```
wiki/
├── index.md      # 목차: Phase별 대분류 → 중분류 → 페이지
├── log.md        # 작업 기록 (최신순)
├── overview.md   # 전체 종합: 프로젝트 목표, 현재 이해, 발전하는 가설, 열린 질문
├── requirements/ # 시스템 요구사항: 기능·비기능·데이터·모델, 탐지 대상 정의. Phase 공통
├── phase_0/      # 데이터셋 구조, 데이터셋 불러오기
├── phase_1/      # 학습
├── phase_2/      # 추론, API 설계
├── phase_3/      # 테스트, 평가
└── phase_4/      # vision task 확장
```

Phase 폴더 안에는 필요한 종류 폴더만 만든다.

```
phase_N/
├── sources/      # 원자료 1개당 요약 페이지 1개
├── entities/     # 구체적 대상: 데이터셋, 모델, 라이브러리, 도구, 코드 모듈
├── concepts/     # 개념·방법론·주제
└── analyses/     # Query 결과 중 남길 가치가 있는 것: 비교표, 분석, 계획
```

- 페이지는 한 Phase 폴더에만 둔다.
- 여러 Phase에 걸친 페이지는 처음 다룬 Phase 폴더에 둔다. 다른 Phase에서는 링크로 가리킨다.
- 빈 Phase 폴더는 `.gitkeep`으로 유지한다.

`index.md` 대분류는 `공통`과 `Phase 0`~`Phase 4`다. 늘리지 않는다.

| 대분류 | 다루는 주제 | 폴더 |
|---|---|---|
| 공통 | 목표, 진행 단계, 요구사항, 탐지 대상 | `overview.md`, `requirements/` |
| Phase 0 | 데이터셋 구조, 전처리, 불러오기, 저장 위치 | `phase_0/` |
| Phase 1 | 학습, 실험 관리 | `phase_1/` |
| Phase 2 | 추론, API | `phase_2/` |
| Phase 3 | 테스트, 평가 | `phase_3/` |
| Phase 4 | vision task 확장 | `phase_4/` |

페이지는 폴더와 같은 대분류 하나에만 올린다. 중분류는 필요할 때 만들고, 20개를 넘으면 나누거나 허브 페이지로 옮긴다.

## 페이지 규칙

- 파일명: 영어 소문자 kebab-case (`social-lstm.md`). 본문은 한국어.
- 본문 링크는 상대 경로 Markdown 링크를 쓴다.
  예: `[AI Hub 101](../entities/aihub-101-cctv.md)`, 다른 Phase는 `[x](../../phase_1/analyses/x.md)`
- 절 링크에는 제목 앵커를 붙인다.
  예: `[2.1절](../entities/aihub-101-cctv.md#21-실제-파일-수)`
- 파일명은 위키 안에서 유일하게 유지한다.
- 아직 없는 페이지는 링크 없이 작성 후보로 적는다.
- 모든 페이지에 YAML frontmatter (Dataview 용):

```yaml
---
type: source | entity | concept | analysis | requirements | overview | adr
tags: []
sources: ["wiki/phase_0/sources/source-page.md"]  # docs/ 기준 경로 목록
created: YYYY-MM-DD
updated: YYYY-MM-DD
---
```
- `sources`에는 `docs/` 기준 파일 경로를 적는다.
- source 페이지 추가 필드: `raw: raw/파일명`, `authors`, `year`, `url`.
- 주장에는 출처 링크를 붙인다.
  예: `[출처](../sources/some-paper-2024.md)`
- 소스 간 **모순**은 지우지 말고 `> [!warning] 모순` callout으로 양쪽을 기록한다.
- 새 소스가 기존 주장을 대체하면 `> [!note] 갱신됨` 으로 이력을 남긴다.
- 추측은 `> [!question]` callout으로 사실과 구분한다.
- 절 참조는 `5.3절`처럼 쓴다. `§` 기호는 쓰지 않는다. 절 번호를 바꾸면 그 절을 가리키는 다른 페이지도 함께 고친다.
- 수치에는 **기준**을 함께 적는다. 예: "라벨에 등록된 이미지 18,212장"과 "실제 이미지 파일 16,911장".
- 같은 사실은 한 페이지에만 자세히 적고, 다른 페이지는 링크로 가리킨다.

## 결정 기록 (ADR)

설계 결정의 이유를 남긴다. 위키 페이지는 무엇을 했는지 적는다. ADR은 왜 그렇게 했는지 적는다.

- 위치: `docs/adr/`. 템플릿: `wiki/.templates/adr-template.md`.
- 파일명: `adr-NNNN-<키워드>.md`. 번호는 4자리로 차례로 붙인다. 쓴 번호는 다시 쓰지 않는다.
- 결정 1개당 파일 1개를 쓴다.
- 아래 세 조건을 모두 만족할 때만 쓴다.
  1. 되돌리기 어렵다.
  2. 맥락 없이 보면 이상하다. 나중에 읽는 사람이 "왜 이렇게 했지?"라고 묻는다.
  3. 실제 선택지가 있었고, 이유가 있어 하나를 골랐다.
- 상태: `제안` → `승인`. 거둔 결정은 `폐기`, 새 결정으로 바뀌면 `대체됨`이다.
- `승인`한 ADR의 맥락·결정·결과는 고치지 않는다. 상태와 `superseded_by`만 바꾼다.
- 결정이 바뀌면 새 ADR을 쓴다. 이전 ADR은 `대체됨`으로 바꾸고 새 ADR을 링크한다.
- 위키 페이지에는 ADR 링크만 단다. 이유는 ADR에만 자세히 적는다.
- `index.md`에는 승인·제안 ADR을 해당 Phase 아래 "결정" 중분류로 올린다. 템플릿은 올리지 않는다.
- ADR frontmatter에는 `status`를 더 적는다. 대체됐으면 `superseded_by`도 적는다.

## 작업 흐름

### Ingest — "ingest 해줘 <파일>"
기본은 **한 번에 소스 하나, 사람과 함께**.
1. `raw/`의 소스를 읽는다 (이미지가 있으면 텍스트 먼저, 그다음 필요한 이미지를 따로 본다).
2. 핵심 요점을 사람과 간단히 논의하고, 무엇을 강조할지 확인한다.
3. `wiki/phase_N/sources/<slug>.md` 요약 작성: 핵심 주장, 방법, 수치/결과, 한계, 이 프로젝트와의 관련성.
4. 소스가 바꾸는 entity/concept 페이지를 생성하거나 갱신한다. 모순·대체 표시.
5. `overview.md`의 종합/가설 갱신.
6. `index.md` 갱신, `log.md`에 항목 추가.

### Query — 질문
1. `index.md`를 먼저 읽고 관련 페이지를 찾아 읽는다 (필요하면 grep).
2. 출처 링크와 함께 답한다. 형식은 질문에 맞게: 문단, 비교표, Marp 슬라이드, matplotlib 차트 등.
3. 재사용 가치가 있는 답은 `wiki/phase_N/analyses/`에 저장하고 index/log 갱신 (사람에게 저장 여부를 제안).

### Lint — "lint 해줘"
점검 후 보고하고, 승인받은 것만 고친다:
- 페이지 간 모순, 새 소스로 낡은 주장
- 인바운드 링크 없는 고아 페이지, index 누락
- 자주 언급되지만 자기 페이지가 없는 개념
- 빠진 교차참조
- 해결된 "미정" 항목, 결정이 바뀐 뒤 남은 옛 표현, 틀린 절 번호
- 웹 검색으로 채울 수 있는 데이터 공백, 다음에 조사할 질문/찾을 소스 제안
