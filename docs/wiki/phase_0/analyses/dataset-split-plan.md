# 데이터셋 분할 계획 — AI Hub 101 Bbox와 110

보행자 검출용 데이터셋을 나누고 만드는 계획이다.

> [!note] 상태 (2026-11-24)
> 분할 방법, 클래스, 라벨 형식, 저장 경로는 결정했다.
> 장소 목록(4.1절)은 검토 전이다.
> 배경 비율과 카메라별 상한은 미정이다(7절).
> mini 데이터셋으로 생성과 학습을 확인했다(8절).

## 1. 쓰는 데이터

| 데이터셋 | 첫 과제에서 | 이유 |
|---|---|---|
| [aihub-101-cctv](../entities/aihub-101-cctv.md) Bbox | 쓴다 | CCTV 시점이고 보행자 상자가 있다 |
| [aihub-101-cctv](../entities/aihub-101-cctv.md) Tracking, Segmantation | 쓰지 않는다 | Phase 4의 후보다 |
| [aihub-095-accident](../entities/aihub-095-accident.md) | 쓰지 않는다 | 상자 라벨이 없다 |
| [aihub-110-child-zone](../entities/aihub-110-child-zone.md) | 쓴다 | 어린이 보호구역 CCTV의 사람 상자가 있다 |

## 2. 문제: 공식 구분은 카메라가 겹친다

- AI Hub의 Validation 카메라 45대는 모두 Training에도 있다. (출처: [aihub-101-cctv 3.1절](../entities/aihub-101-cctv.md#31-규모))
- 고정 CCTV는 카메라가 같으면 배경이 같다.
- 공식 구분을 그대로 쓰면 모델이 배경을 외워도 검증 점수가 높게 나온다.
- 이 점수는 새 카메라에서의 성능을 알려 주지 못한다.

## 3. 분할 방법 비교

| 방법 | 나누는 단위 | 측정하는 것 | 문제 |
|---|---|---|---|
| A. 공식 구분 | AI Hub가 정한 대로 | 같은 카메라의 다른 프레임 | 배경이 겹친다. 점수가 부풀려진다 |
| B. 카메라 단위 | 카메라 ID | 새 카메라 | 한 장소의 카메라들이 같은 장면을 찍을 수 있다 |
| C. 장소 단위 | 장소 이름 | 새 장소 | 장소가 37곳뿐이라 비율을 정확히 맞추기 어렵다 |
| D. 날짜 단위 | 촬영 날짜 | 같은 카메라의 다른 날 | 배경이 겹친다 |

**결정: C. 장소 단위.**

- 이 프로젝트의 목적은 처음 보는 CCTV에서도 보행자를 찾는 것이다. C가 이 목적에 가장 가깝다.
- 같은 영상에서 뽑은 비슷한 프레임도 한쪽에만 들어간다.

## 4. 분할 절차

1. Training과 Validation의 라벨을 합친다. 합계는 이미지 163,913장, 장소 37곳, 카메라 70대다(라벨 기준).
2. 장소마다 보행자가 있는 이미지 수를 센다.
3. 장소를 train, val, test에 배정한다. 목표 비율은 보행자가 있는 이미지 기준으로 70%, 15%, 15%다.
4. 배정할 때 다음을 맞춘다.
   - 세 묶음 모두에 `BC` 카메라와 `SC` 카메라가 들어간다.
   - 세 묶음 모두에 1920x1080과 1280x720 이미지가 들어간다.
5. 배정 결과를 `configs/data/aihub101-ped-v1.splits.yaml`에 적는다. 이 파일을 git에 올린다.
6. test는 Phase 3의 최종 평가에만 쓴다. 학습 중 모델 선택에는 val만 쓴다.

배정은 시드를 고정한 무작위 탐색으로 만든다.
결과 목록은 파일로 고정한다. 다시 실행해도 같은 결과가 나온다.

```bash
docker compose run --rm lab python -m data.split_locations
```

### 4.3 배정 안에서 확인한 점

- `SC` 장소는 카메라가 4~5대다. `BC` 장소는 카메라가 1대다.
- val의 `범박터널-범박1교방향`은 보행자 이미지가 9장뿐이다. 실제로 val에 쓰이는 장소는 3곳이다.
- val의 720 이미지는 `충대오거리`에만 있다.
- test의 `삼정고가교`는 보행자 이미지가 34장이고, `중동IC하부(판교진출)`는 74장이다.
- 범계 두 곳의 카메라 ID는 `BC`나 `SC`로 시작하지 않는다. 두 곳을 합쳐 이미지가 11장이다.
- 장소마다 이미지 수가 1장~14,062장이다.

## 5. 데이터셋 만들기

### 5.1 입력 파일 찾기

[원본 manifest](raw-manifest.md)에서 실제 파일 대응 결과를 확인한다.

1. 각 분할의 JSON을 읽어 이미지 목록을 만든다.
2. 분할, 카메라 ID, 파일 이름으로 JPG를 찾는다.
3. JPG가 없거나 후보가 여러 개면 기록한다.
4. JPG는 복사하지 않는다. 원본 경로를 그대로 쓴다.

입력 경로는 [aihub-101-cctv 2절](../entities/aihub-101-cctv.md#2-폴더-구조)을 따른다.

### 5.2 거르는 기준

| 항목 | 제안 |
|---|---|
| 클래스 | 보행자 1개. 원본 7번을 COCO 카테고리 `person`으로 바꾼다 |
| 오토바이(자전거) 6번 | 넣지 않는다 |
| 보행자가 없는 이미지 | 분할마다 이미지의 10%를 배경 이미지로 넣는다(`background_ratio` 기본값, 미정) |
| 날씨, 시간대 | 거르지 않는다. `manifest.csv`에 기록만 한다 |

### 5.3 라벨 변환

라벨 형식은 COCO JSON으로 정한다(2026-11-21). YOLO TXT는 쓰지 않는다.
YOLO TXT는 이미지 옆 `labels/` 폴더가 필요하다. 원본은 읽기 전용이라 쓸 수 없다.
LibreYOLO 규격은 [데이터셋 형식](../concepts/libreyolo-dataset-formats.md#공통-yaml)을 참고한다.

- 분할마다 JSON 파일 1개를 만든다.
- `images`에 이미지마다 `id`, `file_name`, `width`, `height`를 적는다.
- `annotations`에 상자마다 `id`, `image_id`, `category_id`, `bbox`, `area`, `iscrowd: 0`을 적는다.
- `categories`에는 `{"id": 1, "name": "person"}` 1개만 둔다.
- `[x1, y1, x2, y2]` 픽셀 값을 `bbox: [x, y, w, h]` 픽셀 값으로 바꾼다. 정규화하지 않는다.
- `area`는 `w * h`로 적는다.
- `file_name`은 `data/raw/` 기준 상대 경로로 적는다.
- 경로 앞에 데이터셋 폴더 이름을 넣는다. 110을 섞어도 루트가 같다.
- 이미지 크기는 이미지 파일에서 읽는다. 라벨에 크기가 없다.
- 이미지 밖으로 나간 좌표는 잘라 낸다.
- 잘라 낸 뒤 `w` 또는 `h`가 0 이하인 상자는 버리고 기록한다.
- 배경 이미지는 `images`에만 넣고 `annotations`에는 넣지 않는다.

### 5.4 결과 구조

```text
data/processed/aihub101-ped-v1/
├── annotations/{train,val,test}.json
├── manifest.csv     이미지 1장이 1행
├── issues.csv       버린 항목과 이유
└── metadata.yaml    생성 명령, 인수, 분할별 수

configs/data/
├── aihub101-ped-v1.yaml          LibreYOLO에 넘기는 데이터셋 YAML. 생성 파일이라 git에서 제외한다
└── aihub101-ped-v1.splits.yaml   장소별 분할 목록. git에 올린다
```

생성 명령은 다음과 같다.

```bash
docker compose run --rm lab python -m data.build_coco [name=N fraction=F overwrite=true]
```

- `name` 기본값은 `aihub101-ped-v1`이다.
- `fraction`은 보행자 이미지를 뽑는 비율이다. 기본값은 1.0이다.
- `background_ratio`, `seed` 기본값은 0.1, 0이다.

`issues.csv`의 `issue` 값은 다음과 같다.

| 값 | 의미 |
|---|---|
| `ambiguous` | 원본 manifest에서 후보가 여러 개인 항목. 넣지 않는다 |
| `missing_media` | 라벨에 대응하는 JPG가 없는 항목. 넣지 않는다 |
| `empty_box` | 잘라 낸 뒤 `w` 또는 `h`가 0 이하인 상자. 버린다 |

- 이미지는 복사하지 않는다. 원본 경로가 이미 겹치지 않는다.
- YAML의 `path`는 `/app/data/processed/<이름>`이다. `annotations`는 `path` 기준 경로다.
- YAML의 `train`, `val`, `test`는 모두 `/app/data/raw`로 적는다.
- LibreYOLO는 이 루트와 `file_name`을 이어서 이미지를 읽는다.
- 저장 위치가 바뀌면 `data/raw/` 링크만 고친다.
- HDD가 너무 느리면 이미지를 SSD로 복사한다. 그때는 YAML 루트만 바꾼다.
- YAML의 `names`는 `{0: person}`으로 적는다. COCO의 카테고리 이름과 같아야 한다.
- 폴더 이름에 버전(`v1`)을 넣는다. 거르는 기준을 바꾸면 `v2`를 새로 만든다.

`manifest.csv`는 이미지 정보를 모은 표다. 이미지 1장이 1행이다. LibreYOLO는 이 파일을 읽지 않는다.
`width`와 `height`는 COCO `images` 항목과 같은 값을 쓴다.

| 열 | 내용 | 값 예 |
|---|---|---|
| `file_name` | `data/raw/` 기준 원본 경로 | `101.교통문제_.../01.데이터/.../xxx.jpg` |
| `split` | 분할 | `train`, `val`, `test` |
| `location` | 장소 | 원본의 장소 이름 |
| `camera` | 카메라 ID | `BC01` |
| `weather` | 날씨 | `sunny`, `rainy`, `cloudy`, `foggy`, `snow` |
| `time_of_day` | 시간대 | `dawn`, `morning`, `day`, `afternoon` |
| `width` | 이미지 너비 (픽셀) | `1920`, `1280` |
| `height` | 이미지 높이 (픽셀) | `1080`, `720` |
| `num_persons` | 보행자 상자 수 | `3` |
| `source_split` | AI Hub 원본 분할 | `1.Training` |
| `label_file` | 101 폴더 기준 라벨 JSON 경로 | `01.데이터/.../xxx.json` |
| `label_image_id` | 라벨 JSON의 `images[].id` | `368617` |

값 규칙은 다음과 같다. 코드로 바로 거르고 셀 수 있게 한다.

- 범주 값은 영어 소문자로 적는다.
- `weather`는 원본 `weather` 값을 소문자로 바꾼다.
- `time_of_day`는 원본 `time_space` 값을 바꾼다.

| 원본 `time_space` | `time_of_day` |
|---|---|
| 새벽 | `dawn` |
| 오전 | `morning` |
| 낮 | `day` |
| 오후 | `afternoon` |

- 표에 없는 원본 값은 `unknown`으로 적고 로그에 남긴다.
- `width`, `height`는 원본 `resolution`이 아니라 이미지 파일에서 읽는다. 원본 `resolution`에는 빈 값이 있다.
- `num_persons`는 변환 후 남은 상자 수다.
- 파일은 UTF-8, 쉼표 구분, 첫 행 열 이름으로 쓴다.

- `file_name`은 COCO `images` 항목의 `file_name`과 같은 값을 쓴다. 이 열로 두 파일을 잇는다.
- `manifest.csv`는 COCO JSON과 같은 실행에서 만든다. 두 파일이 어긋나지 않게 한다.
- `manifest.csv`를 손으로 고치지 않는다. 바꿔야 하면 변환을 다시 실행한다.
- `lab`에서 만들고 분할을 검증한다. 분할마다 `BC`/`SC` 카메라와 두 해상도가 있는지 센다.
- 학습에서는 결과를 읽는다. 평가 결과와 이어서 조건별 성능을 본다.

### 5.5 진행 순서

1. 작은 데이터셋(`mini`, 약 5,000장)을 먼저 만든다. 변환 코드와 불러오기를 빨리 확인한다. (완료, 8절)
2. 확인이 끝나면 전체(`v1`)를 만든다. (예정)

## 6. AI Hub 110 사용 계획

110은 101과 촬영 환경과 해상도가 다르다.
영상의 연속 프레임은 서로 비슷하다.
현재 데이터에는 라벨과 이미지가 없는 짝도 있다.

1. `driveway_walk`의 JPG와 XML 대응을 먼저 확인한다.
2. 대응이 확인된 `person` 상자를 COCO 카테고리 ID 1로 변환한다. YAML의 모델 클래스 ID는 0이다.
3. 같은 영상의 프레임은 한 분할에 둔다.
4. 촬영 장소를 확인할 수 있으면 장소 단위로 나눈다.
5. 연속 프레임은 일정 간격으로 뽑는다.
6. 101 기준 모델과 101·110 혼합 학습 모델을 비교한다.
7. 두 모델에 같은 평가 묶음을 쓴다.
8. 101과 110의 평가 결과를 각각 기록한다.

혼합 비율과 프레임 추출 간격은 전처리에서 정한다.
110의 평가 영상은 두 모델의 학습에서 제외한다.

## 7. 정해야 할 것

- [x] 분할 방법: 장소 단위(C)로 정했다.
- [x] 클래스: 보행자 1개(`person`)로 정했다.
- [x] 저장 경로: 결과는 `data/processed/`, 임시 파일은 `data/interim/`에 둔다. 이미지는 복사하지 않는다.

  - 인접 장소를 한 묶음으로 볼지 정한다(4.3절).
  - 범계 두 곳의 카메라 ID를 확인한다.

- [ ] 같은 카메라의 프레임 수에 상한을 둘지. 카메라마다 1장~7,064장으로 차이가 크다. 현재 상한은 없다.

### 8.2 학습 확인

LibreYOLO 1.8.0으로 1 epoch를 학습했다.

```bash
docker compose run --rm lab libreyolo train --data configs/data/aihub101-ped-mini.yaml \
  --model yolox-s --epochs 1 --cache false \
  --project outputs/runs --name smoke-mini
```

| 항목 | 값 |
|---|---|
| 모델 | `yolox-s`, 입력 640, batch 16 |
| 학습 시간 | 약 72초/epoch (약 54장/초) |
| val mAP50 | 0.445 |
| val mAP50-95 | 0.212 |
| val mAP_small | 0.029 |

- 이 수치는 동작 확인용이다. 성능 비교에 쓰지 않는다.

### 8.3 주의할 점

- `--cache disk`를 쓰지 않는다. 이미지 옆에 `.npy`를 쓰려다 실패한다. 원본은 읽기 전용이다.
- 가중치는 프로젝트 루트의 `weights/`에 내려받는다. git에서 제외한다.
- 다음 경고는 무시한다.
  - `No images found for split ... at /app/data/raw`. COCO 경로로 이미지를 읽으므로 학습에 문제가 없다.
  - 로그 경로에 `//`가 보이는 표시.
  - `faster_coco_eval`이 없다는 경고.
